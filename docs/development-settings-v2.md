# Offline comparison settings, revision 2

Status: offline software interface, not execution authorization. Files retain their original additive filenames; the required configuration version is development-comparison-settings-v2 and message version is provider-neutral-messages-v2. This replaces v1 settings behavior only. Existing v3 instances, evidence, prior patch/index and v2 development exports remain immutable.

## Configuration

JSON-only: load(text) accepts at most 65,536 UTF-8 bytes, strict duplicate-key/non-finite rejection and no environment reads or overrides. All unresolved selections in development-settings-v1.example.json remain null; an unchanged example is deliberately invalid. Required fields are version, provider, model_revision, corpus_version, manifest_sha256, case_ids, repetitions, spending_ceiling, currency, spending_scope, token_limit, wall_seconds, tool_call_limit, retry_limit, order and seed. No implicit defaults or repairs occur.

Currency currently supports USD only, explicitly selected. Spending scope must be entire_explicit_plan_all_arms_repetitions: the ceiling covers the aggregate selected corpus plan across both arms and every repetition, including operational failures and any billable tool/provider work. No per-attempt multiplication is inferred. There are no retries in this compatibility interface. This is an accounting declaration, not price verification, currency conversion, metering or spend enforcement. A zero ceiling is valid syntax but cannot authorize paid calls. Allowed amounts are finite, nonnegative and below the software representation cap of 1,000,000 USD; no amount is approved by validation.

Repetitions 1..10 and selected IDs 1..128 match the existing registration consumer per package. Larger plans require an explicitly supported later interface rather than silent truncation. Tokens and wall seconds are positive signed-31-bit integers; seed is unsigned-32-bit, tool calls 0..4, retries exactly zero. Order is case_then_arm or arm_then_case. These are compatibility/validation limits, not approved experiment quantities or resource allocations. In particular the local 60-second verification-command cap is not a team per-attempt research budget. Validation of a 120-second synthetic configuration does not execute or allocate it.

Unknown keys, including secret-like keys, are rejected. Allowed text values are not a secret detector: users must never put credentials in any field. Diagnostics do not interpolate field values. Missing, null, boolean-as-number, malformed types and non-finite values fail with ValueError. Provider/model strings are labels only; no supported provider serialization is inferred.

## Syntax versus binding

validate/load only check syntax. bind(config, directory, plan, pins) additionally requires the supported seeded-development-suites-v2 corpus and explicit exact current source hashes from source_pins(). The caller must review/pin that identity; a freshly calculated fingerprint alone is not authorization. Pins cover this interface, registration, generator/auditor, text input view/instructions, contract, checker, oracle, CSP tool and text renderer. The exact interface SHA is recorded in the separate revision index.

Configuration corpus, manifest SHA, selected ID order and repetitions must equal the registration plan. Existing registration preflight then requires exact plan fields, registration/input versions, consumer and instruction identities, both arms, audited package hashes/source identities and accepted evidence-eligible membership. Unknown, quarantined, mixed-version or incomplete plans fail closed. Audit is bounded by the existing consumer; it recomputes mathematical/tool checks but cannot authenticate historical invocation receipts. bind returns offline_bound_not_execution_authorization, selected count and evaluator-side copies of the plan/config/pins. It does not select provider, pricing or protocol on behalf of the team.

V3 targeted-interactions-development-v3 is explicitly unsupported by this binding. Its trusted-local replay/input projection remains separate; its 56 empty software slots are not tested scorer integration. A later explicit v3 consumer must preserve planned denominator failure behavior before a real comparison. There are 48 v3 candidates / 28 normalized structures, and 28 feasible admissions / 17 normalized structures, grouped by family/base as related controls.

## Prepared message assembly

assemble(arbitrary_text, ...) always rejects. prepare requires the explicit audited v2 package/plan/pins, then obtains the existing registration's field-only prepared payloads. It emits only system and user messages: system is exact shared instruction plus the arm instruction, user is exact prepared instance text. Plan IDs, gold, labels and source metadata remain evaluator-side in a separate binding result. The text-only arm declares no tools; the CSP arm declares the same pinned merged schema-1.1 model-translated tool for every compared model. This declaration is not live tool wiring. Provider-specific role/tool support must be verified in a separately reviewed adapter; there is no fallback or provider call here.

Tests assert syntax errors, source-pin drift, plan mismatch/incomplete plans, unknown membership, v3 rejection, prepared-role equality and no join ID in model messages. The existing registration's empty-receipt assessor is exercised for a small synthetic accepted plan, retaining planned/missing slots and zero success. That v2 test does not establish v3 scorer integration, live budget enforcement or provider compatibility. Original scoring/failure rules remain untouched.
