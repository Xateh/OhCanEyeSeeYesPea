# Paired provider integration: v3 correctness revision

This is software wiring, tested only with deterministic fake transports. It is not a live validation, provider selection, spending approval or accepted research protocol. No model command, authentication check or prompt transmission was performed for this revision.

## Interface and explicit opt-in

At this integration revision's introduction, `paired_runner.VERSION` was `paired-development-runner-v3`. The current runner and config template use `paired-development-runner-v4` after the [P2 accounting correction](benchmark-p2-local-fixes.md); historical plans retain their original source/version identities. Existing Python fixture settings without the two new keys are explicitly recorded as `execution_mode="fixture", provider_binding=null` in the resulting plan. Fixture mode requires an offline provider. It cannot construct the Claude adapter. Archived v1 plans and receipts remain unchanged and are not silently converted or resumed under v2 source identities.

For the optional Claude route, set `execution_mode="claude_live"`, `provider_revision="claude-paired-text-json-v2"` and a binding returned by `claude_pair_adapter.binding(model, effort, call_wall_seconds, call_budget_usd)`. The returned binding pins adapter, merged provider and prompt source SHA256 (including accounting, strict JSON and retention code), Python runtime identity, retention policy, serialization revision, exact requested model string, effort, explicit per-call timeout and USD allocation. Source changes require a fresh explicit plan. The plan also pins existing dataset, checker, solver and common/arm instruction identities. A model alias is not an independently verified immutable provider revision; review the provider's exact supported identifier before a study.

`paired_runner.run(specs, settings, new_directory, provider_factory=None, allow_live=True)` is the live-capable software entry. Both the recorded live mode and this separate flag are required. The default is false. A live factory must return the exact source-pinned `ClaudePairAdapter`; arbitrary providers cannot bypass fixture mode. Mock tests inject only the transport at that adapter boundary. Construction and preflight never call the CLI.

The CLI is `python3 tools/run_paired.py --datasets DATASETS.json --config CONFIG.json --out NEW_DIRECTORY`. Only a deliberately live configuration plus `--allow-live` can reach the existing CLI transport. This command was not run in live mode here. The JSON example leaves unresolved selections null and deliberately fails run-ready validation until filled. There are no environment overrides or secret fields. Do not put credentials in configuration or receipts.

## Inputs and actual serialization

The initial case text is identical across arms and is the approved versioned actual-ID input view. The system content is the pinned shared instruction plus arm instruction. The merged `SYSTEM_V1` adds the one-JSON-object rule. The no-tools arm has no CSP schema/history. The CSP arm receives the same pinned schema and text-protocol exposure for every compared model; only model-submitted translated instances reach the checked solver.

This reuses `ClaudeCodeProvider.next`, its isolated temporary working directory, tool-free CLI arguments, `study.prompts.user_message('v1', ...)`, envelope accounting and exact requested-model check. It is a JSON text tool-call protocol, not native tool invocation. Each turn starts an isolated subprocess; earlier submitted instances/results are serialized into the next user message using the merged history serializer. The CLI itself has no tools, user settings, MCP servers or persistent session. The prior v2/v3 study prompt variants and their unrelated numerical examples are not selected or edited.

The new serialization is `merged-user-message-v1-strict-unfenced-json-exact-output-span-v1`. Unlike the historic parser, it rejects fences, duplicate keys, non-finite JSON and extra protocol fields. It extracts the final output's exact substring without rewriting whitespace or repairing evidence. Frozen intended-instance scoring then checks that raw output. Historic parser behavior and old results are preserved.

## Evidence, errors and limits

Ordinary returned attempts include `provider_calls` (large resource failures retain the original in an evidence file): original CLI stdout envelope, original model text when recoverable, serialized request/arguments, effective per-call USD allocation and timeout, elapsed time, direct CLI exit status when the real transport returns, and error class. A nonzero exit cannot be accepted as a successful final even if stdout contains valid JSON. Invalid JSON and provider/model errors retain independently observed envelope usage. A timeout retains available partial stdout; byte partials are decoded with replacement explicitly, so this field is not a binary archive. Raw stderr/exception messages are not persisted, since CLI diagnostics may contain sensitive information. They are not represented as complete raw error logs. Receipts contain private development prompts and require the same access controls as the dataset.

The runner subtracts observed prior tokens/cost and elapsed wall time before another turn. Unknown token/cost observations stop further turns. Unknown cost stops new planned slots. Known exhausted whole-plan cost stops new slots; missing slots remain in denominators. Known over-limit attempts remain failures, not discarded or retried. Missing usage stays unknown; evidence success is separate from operational success, and unknown budget accounting prevents a compliant success claim. No automatic retries, replacement, overwrite or cross-version resume exists.

The adapter replaces the historic 300-second/$2 defaults with explicit recorded values. The effective timeout is the smaller of per-call timeout and remaining attempt wall time; the CLI USD argument is the smaller of per-call allocation and observed remaining whole-plan allocation. These are software controls, not agreed experimental quantities. Token usage includes the merged cache-token accounting. No supported hard output-token limit is supplied by this CLI adapter: token checks are post-return, and further turns are refused when exhausted. Shared/tool-history tokens are counted as reported on each isolated call.

`subprocess.run(timeout=...)` bounds the direct CLI subprocess and kills/waits for that process on timeout. It does not guarantee cancellation of descendants, a remote request or remote billing. The CLI's max-budget flag and observed scheduling ceiling are not an independently verified hard dollar cap. Checked solver and arbitrary fixture callbacks remain cooperative/post-return. A killed/interrupted process can have unknown final usage/spend. If Python is interrupted during an active call, the saved immutable plan and previous flushed attempts remain assessable; the active slot stays missing, and its in-memory partial ledger may be unavailable. This is not crash-atomic call journaling. No hard end-to-end cancellation/budget claim is made.

## Before real execution

Select corpus IDs/repetitions/order/seed and model revision/effort; pin and review source and prompt/serialization identities; choose token/wall/tool/call/whole-plan limits; review provider availability, pricing, CLI behavior and authorization outside this offline task. Secrets are managed externally by the existing provider, never loaded by settings. Other provider adaptations fail closed and require separate serializer/usage/cancellation validation. Software tests do not establish installed CLI compatibility, authentication, billing behavior, live tool reasoning or team acceptance.

## Correctness revision: call allocations and retained evidence

Each transport record now retains its observed usage and effective per-call allocation, with a recomputed cost_violation flag. Summaries join these observations to call accounting, verify allocations against the pinned per-call ceiling and remaining whole-plan ceiling, and classify call_budget_violation separately and within budget_violation. A call overrun stays a failure even below the whole-plan ceiling; its raw response and observed cost are retained. No further turn or new slot starts after an observed overrun. Missing planned slots remain in denominators; no replacement or retry occurs. This detects observed overruns, not an independently enforced billing cap.

The plan and provider binding pin paired_receipts.py and its policy. Ordinary JSONL receipt lines are limited to 8 MiB, including their newline. Larger complete receipts are written unchanged to an exclusive evidence-ATTEMPT_ID.json file, with a bounded hash/size/attempt reference in attempts.jsonl. Run and assessment apply the same storage rules. The attempt becomes an explicit resource_bound failure and new slots stop. Up to 64 MiB of archived original JSON can be read, hash-verified and parsed for assessment; the original raw/error/usage/tool evidence remains unchanged in that file. The resource-error outcome is applied separately: a previously well-formed final remains answer-complete, and original provider-error flags remain unchanged, while operational success is false. Opaque unparsed evidence cannot establish answer completion. Regular-file, reference-identity, byte and line/count checks precede parsing; unsupported, incomplete, missing, rehashed-routing or symlink references fail closed.

Beyond the 64 MiB parse bound, the already returned original is still retained as opaque evidence, and a small failed-attempt record preserves routing, observed usage/allocation and tool/event counts. Assessment checks its file metadata but does not read, parse or hash that oversized body. The opaque_evidence counter explicitly identifies this unverified retained evidence; it can never yield a compliant success or validate model evidence. A same-size mutation of an opaque file is therefore not detected by this bounded assessment. Such a body needs separate manual review. The stored digest records what was written, not proof that historical invocation or later opaque contents were authenticated.

Serialized provider requests are bounded at 1 MiB before starting transport; refused requests record zero CLI usage because no CLI call started. Returned CLI envelopes are limited to 1 MiB for parsing. Oversized returned data is retained and causes resource_bound, with unknown usage when it cannot be safely parsed. Existing subprocess capture and arbitrary injected callbacks can allocate data before these post-return checks. Original evidence retention has no hard disk-quota enforcement; storage failure or interruption may leave an incomplete run, whose plan/previous flushed slots remain assessable. These are software retention/assessment limits, not a newly approved research budget or a hard process-memory/storage cap.

Previous v2 plans, patches, passing and failing receipts remain preserved. New revisions are not silently resumed or substituted for them. No new live validation occurred.
